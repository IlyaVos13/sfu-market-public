# ADR-001 Монолитная серверная архитектура
Дата: 02.10.2026. Статус: принято как проектное решение.

## Контекст
Команда из двух студентов разрабатывает площадку объявлений. Регистрация, публикация, модерация, жалобы и уведомления используют связанные данные. Нагрузка на начальном этапе небольшая; необходимо понимать и демонстрировать полный запрос от интерфейса до базы.

Рассмотрены монолит ASP.NET Core с отдельным браузерным интерфейсом и набор микросервисов с отдельными хранилищами. Микросервисы потребовали бы сетевых контрактов, согласования данных и обслуживания нескольких приложений без подтвержденной потребности.

## Решение
Использовать один Backend API на ASP.NET Core, интерфейс React, одну PostgreSQL и файловое хранилище фотографий. Разделять серверный код на контроллеры, сервисы бизнес-правил и слой работы с данными. Доступ к БД и файлам выполняет только сервер. Обмен UI и API - HTTP/JSON через HTTPS, изображения - multipart/form-data; в production один origin. Identity отвечает за учетные записи и роли.

Контейнер C4 означает приложение или хранилище, а не обязательный Docker-контейнер. На этом этапе Docker не требуется. Внешние контакты и карты открываются ссылками в браузере; прямой обмен сервера с API Telegram/VK не планируется.

## Последствия
Плюсы: единый запуск и журналирование, простая транзакционная модель, меньше инфраструктуры, понятное распределение обязанностей. Минусы: серверные модули выпускаются вместе, сбой единственного сервера влияет на весь сервис, локальные файлы усложняют добавление нескольких экземпляров API.

Начальный путь масштабирования - индексы, пагинация и вертикальное увеличение ресурсов. Пересмотр решения нужен, если NFR-M1 не достигается после измерений и оптимизации. Перед горизонтальным масштабированием потребуются общее хранилище фото и согласованное хранение ключей защиты cookie. Принятие ADR не означает, что доступность или производительность уже проверены.
